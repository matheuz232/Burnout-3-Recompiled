# R5900 SetupHeap HLE v0 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Implement and CI-validate the smallest production `SetupHeap` (`0x3d`) HLE required to cross Burnout 3's next real EE startup syscall while preserving all guest architectural state and guest memory.

**Architecture:** Extend the existing stateful Windows `R5900HostSyscallService` with a lightweight `R5900SetupHeapContext`. `SetupHeap` depends on the previously committed main-thread `R5900SetupThreadContext::stack_base`; Burnout's `heap_size == 0xffffffff` path derives `heap_end` from that stack base, while validated positive explicit sizes use `heap_start + heap_size`. The dispatcher interface and generated x64 path remain unchanged.

**Tech Stack:** C++20, CMake, Visual Studio 2022/MSVC x64 Release, existing R5900 IR/execution state and Windows dispatcher, GitHub Actions Windows CI, CTest.

**Spec:** `docs/superpowers/specs/2026-09-06-r5900-setupheap-v0-design.md`

## Global Constraints

- Target remains Windows 10/11 x64 with Visual Studio 2022; do not add a runtime dependency on PCSX2 or another emulator.
- Work only on `design/r5900-setupheap-v0` until an explicit integration decision is made.
- The branch starts from integrated `feature/r5900-or-v0` head `b031b39354afa4ea65aa2339f76ceb596e67df61` plus the approved SetupHeap spec/plan commits.
- Do not merge or modify `main`, the PR #22 base branch, or another integration branch during implementation.
- Do not commit, upload, embed, or derive repository fixtures from proprietary Burnout 3 ELF/data bytes. The user's lawful `SLUS_210.50` remains external-only diagnostic input.
- `SetupHeap` selector is exactly `0x3d`; ABI inputs are low32 `GPR4/a0 = heap_start` and low32 `GPR5/a1 = heap_size_raw`.
- Public API semantics are `void SetupHeap(void*, s32)`: successful SetupHeap must preserve `GPR2/v0` and every other guest architectural register.
- `heap_size_raw == 0xffffffff` means derive `heap_end = setup_thread_context.stack_base`.
- Positive explicit size means `heap_end = heap_start + heap_size_raw`, with unsigned 32-bit overflow protection and `heap_end <= stack_base`.
- SetupHeap requires a previously successful SetupThread context in v0.
- `heap_size == 0`, negative sizes other than `-1`, overflow, missing SetupThread, automatic-size `heap_start >= stack_base`, and explicit overlap past `stack_base` return `Fault` transactionally.
- A successful SetupHeap mutates only host-side `setup_heap_context_`; it performs no guest-memory write and no guest architectural mutation.
- A later successful SetupHeap atomically replaces the previous heap context; a failed/unsupported request preserves it.
- A later successful SetupThread invalidates the previous heap context only after SetupThread validation succeeds; a failed/unsupported SetupThread preserves it.
- `EndOfHeap` (`0x3e`), allocator behavior, scheduler/thread manager, automatic-stack SetupThread, graphics, DMA/IOP, audio, and input remain out of scope.
- Keep `IR5900HostSyscallService`, `r5900_block_dispatcher.h/.cpp`, and CMake target topology unchanged unless a concrete failing test proves the approved design cannot be implemented without changing them. If that happens, stop and revise the design rather than silently widening scope.
- Preserve the existing legal-data policy and do not claim game boot, rendering, menu, or gameplay from this milestone.
