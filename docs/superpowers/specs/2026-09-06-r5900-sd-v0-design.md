# R5900 SD / Store64 + EE Main RAM v0 Design

Date: 2026-09-06
Branch: `design/r5900-sd-v0`
Base: `feature/r5900-or-v0 @ 37ce055ab1d2fbbad73aa3f3fd39b356f981af0e`
Status: design approved in chat; implementation not started

## 1. Purpose

Advance Burnout 3 startup beyond the first real post-SetupHeap boundary by implementing the R5900 `SD` instruction and the minimum EE main-RAM backing required for the real stack store at guest PC `0x0011510c`.

The implementation must preserve the existing native Windows x64 architecture, remain independent of PCSX2 at runtime, avoid proprietary game bytes/assets in the repository, and continue to report unsupported behavior precisely rather than pretending the game boots.

## 2. Real startup evidence

The validated startup path currently reaches:

```text
0x001001e4  syscall SetupHeap
0x001001e8  jal 0x00115108
0x001001ec  nop
0x00115108  addiu sp,sp,-16
0x0011510c  sd ra,0(sp)
0x00115110  jal 0x00114ed0
0x00115114  nop
```

At the call into `0x00115108`:

```text
sp = 0x02000000
ra = 0x001001f0
```

After the prologue `addiu sp,sp,-16`:

```text
sp = 0x01fffff0
```

The required store is therefore:

```text
mem64[0x01fffff0] = 0x00000000001001f0
```

The existing ELF-backed memory currently ends at `0x01ecea00`, so the stack address is not backed by the current `Ps2MemoryMap` even though it is valid EE main RAM.

## 3. Scope classification

This is an architectural change because it modifies shared internal contracts across:

- guest memory backing and translation;
- guest memory callback ABI used by the IR executor and x64 backend;
- R5900 IR opcode set;
- IR validation;
- interpreted execution;
- x64 lowering/execution;
- dispatcher eligibility and memory-fault handling;
- startup integration tests.

## 4. Goals

1. Model EE main RAM as 32 MiB of zero-initialized writable guest memory at `0x00000000..0x01ffffff`.
2. Preserve ELF `PT_LOAD` metadata in `Ps2MemoryMap::regions()`.
3. Copy ELF `PT_LOAD` file bytes into EE RAM and retain zero-filled BSS tails.
4. Allow translated reads/writes anywhere in EE main RAM, including heap and stack space outside `PT_LOAD` ranges.
5. Add a 64-bit guest-memory write callback parallel to the existing 128-bit callback.
6. Lower R5900 `SD` into a new IR opcode `Store64`.
7. Execute `Store64` in both the interpreted IR executor and native x64 backend.
8. Preserve exact memory-fault PC/address/width reporting.
9. Allow the real startup sequence to execute the `SD` at `0x0011510c` and proceed to the following `JAL`.
10. Keep all current tests and pacing/package gates green.

## 5. Non-goals

This milestone does not implement:

- `LD`, `SW`, `LQ`, or other load/store instructions beyond existing support;
- exception vectors, TLB, virtual-memory translation, or R5900 address-error exception delivery;
- scratchpad RAM;
- GS/IOP/VU memory regions;
- cache coherency or hardware MMIO;
- stack growth policies;
- heap allocator behavior;
- `EndOfHeap` syscall;
- scheduler/threading;
- graphics, audio, input, DMA, GS, IOP, or VU execution;
- a claim that Burnout 3 boots or is playable.

## 6. EE main RAM model

### 6.1 Physical range

`Ps2MemoryMap` will provide zero-initialized backing for exactly:

```text
base      = 0x00000000
size      = 0x02000000
exclusive = 0x02000000
```

A byte access is inside v0 main RAM when the full requested range fits in that interval.

### 6.2 `regions()` semantics

`regions()` continues to describe ELF `PT_LOAD` metadata only.

It must not synthesize a fake `PT_LOAD` covering all 32 MiB merely because physical RAM is now backed.

This distinction is intentional:

- `regions()` answers: "what did the ELF declare?"
- `translate()` answers: "what guest RAM can the runtime access?"

### 6.3 `translate()` semantics

For addresses inside EE main RAM, `translate(address, length)` must return a span over the main-RAM backing even if the range is outside every ELF `PT_LOAD`.

Consequences:

- heap and stack ranges become readable/writable;
- memory outside ELF segments begins zero-filled;
- an access crossing a `PT_LOAD` boundary but remaining within EE main RAM is valid;
- existing tests that treated a `PT_LOAD` boundary as a mapping boundary must be updated.

An access that extends beyond `0x02000000` remains unavailable in v0.

### 6.4 ELF loading

`Ps2MemoryMap::from_elf()` must:

1. validate each `PT_LOAD` range using 64-bit arithmetic;
2. reject overlapping ELF `PT_LOAD` metadata exactly as today;
3. reject any `PT_LOAD` whose complete guest range is outside EE main RAM v0;
4. allocate 32 MiB main RAM zero-filled;
5. copy each segment's file bytes at its `p_vaddr` offset;
6. leave each segment's `p_memsz - p_filesz` BSS tail zero-filled;
7. preserve segment metadata and flags in `regions()`.

A new explicit build error should represent a load segment outside supported EE main RAM rather than overloading `AddressOverflow` when the arithmetic itself is valid.

### 6.5 Allocation failure

Failure to allocate the 32 MiB backing must return `Ps2MemoryMapBuildError::AllocationFailed` without a partially usable memory object.

## 7. Guest-memory callback ABI

The current execution context exposes only a 128-bit write callback. Add:

```cpp
using R5900GuestWrite64Fn = bool (*)(void* user,
                                     std::uint32_t address,
                                     std::uint64_t value) noexcept;
```

`R5900GuestMemoryAccess` becomes conceptually:

```cpp
struct R5900GuestMemoryAccess {
    void* user{};
    R5900GuestWrite64Fn write64{};
    R5900GuestWrite128Fn write128{};
};
```

Existing `Store128` behavior must remain unchanged.

The dispatcher must provide both adapters when executing native blocks.

## 8. R5900 `SD` semantics

### 8.1 Decode

The existing decoder already recognizes primary opcode `0x3f` as:

```text
R5900Instruction::Sd
class = Store
width = Doubleword64
```

No decode behavior change is required beyond regression coverage.

### 8.2 Effective address

For `SD rt, imm(rs)` v0:

```text
base32  = low32(GPR[rs].low64)
offset  = sign_extend16(imm)
address = uint32(base32 + offset)
```

The addition is modulo 32 bits.

### 8.3 Alignment

`SD` requires an 8-byte aligned effective address.

If `address & 7 != 0`, v0 reports a memory access failure at the exact guest PC instead of emulating an R5900 exception vector.

The address must not be rounded down or otherwise normalized.

### 8.4 Source value

The stored value is exactly:

```text
GPR[rt].low64
```

`GPR[rt].high64` is ignored.

The write is little-endian through `Ps2MemoryMap::write_u64()`.

### 8.5 Architectural state

Successful `SD`:

- does not modify any GPR;
- does not modify HI/LO/HI1/LO1;
- does not modify SA;
- does not modify FPR/FCR31/FP accumulator;
- modifies only guest memory.

Failed `SD`:

- reports failure before any later guest instruction executes;
- does not modify guest memory;
- does not modify architectural CPU state.

## 9. IR design

Add:

```cpp
R5900IrOpcode::Store64
```

Lowering shape:

```text
opcode      = Store64
destination = none
write_mode  = None
inputs[0]   = base GPR rs
inputs[1]   = value GPR rt
inputs[2]   = signed immediate
```

This mirrors the existing `Store128` operand layout so memory stores remain structurally uniform.

## 10. IR validation

`Store64` validation must require:

- no destination;
- `write_mode == None`;
- exactly three inputs;
- input 0 is a valid GPR;
- input 1 is a valid GPR;
- input 2 is an immediate;
- immediate fits signed 16 bits.

Malformed IR must fail validation before execution or native compilation.

## 11. Interpreted executor

The interpreted `Store64` path must:

1. calculate the 32-bit effective address;
2. set `current_memory_guest_pc` to the `SD` guest PC;
3. reject misalignment;
4. require `context.memory.user` and `context.memory.write64`;
5. invoke `write64(user, address, source_low64)`;
6. on failure populate:

```text
active      = true
access      = Store
guest_pc    = SD guest PC
address     = effective address
width_bytes = 8
```

7. return `MemoryAccessFailure`;
8. stop before subsequent IR executes.

## 12. Native x64 backend

### 12.1 Helper

Add a native helper parallel to `r5900_native_store128`:

```cpp
bool r5900_native_store64(R5900IrExecutionContext* context,
                          std::uint32_t address,
                          std::uint64_t value) noexcept;
```

It is responsible for callback availability/failure and fault metadata.

### 12.2 Helper frame

`sequence_needs_helper()` must return true for either `Store64` or `Store128`.

A block containing both kinds of stores uses the existing single helper-frame mechanism.

### 12.3 Emission

Native `Store64` must:

- preserve the execution context across helper calls using the existing Win64 helper-frame convention;
- calculate the same 32-bit effective address as the interpreted executor;
- reject misalignment without performing the write callback;
- pass context/address/value using Win64 calling convention;
- return block execution failure when the helper reports false;
- preserve all guest CPU state except guest memory.

Interpreted and x64 semantics must match exactly.

## 13. Dispatcher integration

Add `R5900Instruction::Sd` to the v0 eligible instruction set.

Add a dispatcher adapter:

```cpp
bool ps2_memory_write64_adapter(void* user,
                                std::uint32_t address,
                                std::uint64_t value) noexcept;
```

It forwards to `Ps2MemoryMap::write_u64()`.

Every native execution context constructed by the dispatcher must receive both `write64` and `write128` callbacks.

The existing boundary-prefix fix remains unchanged: an unsupported instruction before a later transfer still prevents that transfer from entering the compiled prefix.

## 14. Dispatcher accounting

A successfully executed `SD` counts as one guest instruction inside its native block.

A memory fault at `SD` must report:

- `R5900DispatchStopReason::MemoryAccessFailure`;
- `next_pc == SD guest PC`;
- `width_bytes == 8` in the underlying memory-fault metadata;
- `instructions_executed` containing only instructions completed before the failing `SD`.

No later control transfer or delay slot may execute after a failing `SD`.

## 15. Burnout startup acceptance case

A startup-shaped fixture must represent:

```text
0x001001e8  jal   0x00115108
0x001001ec  nop
0x00115108  addiu sp,sp,-16
0x0011510c  sd    ra,0(sp)
0x00115110  jal   0x00114ed0
0x00115114  nop
```

Initial state:

```text
sp = 0x02000000
```

After the first JAL:

```text
ra = 0x001001f0
```

After the prologue:

```text
sp = 0x01fffff0
mem64[0x01fffff0] = 0x00000000001001f0
```

The dispatcher must then take the JAL at `0x00115110` and produce:

```text
ra      = 0x00115118
next_pc = 0x00114ed0
```

The exact next unsupported boundary beyond `0x00114ed0` is deliberately not specified by this milestone; it must be measured after implementation with the lawful external ELF.

## 16. TDD coverage

Implementation must proceed RED -> GREEN with focused tests covering at least:

### 16.1 Memory map

- 32 MiB EE main RAM is zero-filled;
- `regions()` still reports only ELF `PT_LOAD` metadata;
- bytes outside `PT_LOAD` but inside main RAM translate successfully;
- access crossing an ELF segment edge but remaining in main RAM succeeds;
- `write_u64/read_u64` round-trip at `0x01fffff0`;
- access crossing `0x02000000` fails;
- valid-arithmetic `PT_LOAD` outside v0 main RAM is rejected with the new explicit error;
- ELF overlap detection remains intact;
- BSS zero-fill remains intact.

### 16.2 IR lowering and validation

- decoded `SD` lowers to exactly one `Store64`;
- operand order is base/value/immediate;
- signed immediate is preserved;
- malformed destination/write mode/input counts/kinds/registers/immediate ranges reject.

### 16.3 Interpreted execution

- aligned store succeeds;
- only low64 is written;
- negative offset calculation is correct;
- 32-bit address wrap semantics match design;
- misaligned address fails with width 8 and exact PC;
- missing callback fails;
- callback rejection fails atomically;
- later IR is not executed after failure;
- CPU registers remain unchanged.

### 16.4 Native x64

- `Store64` compiles and executes;
- native bytes use helper-frame path;
- native result matches interpreted result;
- aligned write succeeds;
- misalignment fails before write;
- helper rejection reports exact PC/address/width;
- mixed `Store64`/`Store128` sequence remains valid.

### 16.5 Dispatcher

- `SD` is eligible;
- `ADDIU -> SD -> JAL -> NOP` executes in architectural order;
- real stack address/value are stored;
- failing `SD` does not execute later JAL;
- cache replay preserves memory behavior and failure accounting;
- prior boundary-prefix regression tests remain green.

## 18. Branch and integration policy

Development starts only after this spec is approved and a formal implementation plan is written.

Implementation will occur on an isolated branch derived from this design branch or its exact approved head.

`main`, the PR #22 base branch, and PR merge state must not be changed implicitly.

## 19. Expected milestone outcome

When complete, the runtime should be able to progress from the already validated SetupHeap path through:

```text
JAL 0x00115108
ADDIU sp,sp,-16
SD ra,0(sp)
JAL 0x00114ed0
```

with real EE stack memory backing and native `Store64` semantics.

The milestone ends at the next empirically observed unsupported boundary, whatever that boundary is.
