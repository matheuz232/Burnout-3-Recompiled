# R5900 DADDU v0 Design

Date: 2026-09-06

Branch: `design/r5900-daddu-v0`

Base: `feature/r5900-or-v0 @ 9cfe55f9b3a68038849f20084ac9e30c00adc54e`

## 1. Purpose

Implement the minimum R5900 `DADDU` support required to advance Burnout 3 startup beyond the currently confirmed real boundary:

```text
0x00114edc  03a0202d  DADDU a0,sp,zero
```

The implementation must preserve the existing decoder -> IR -> validation -> interpreted executor -> Windows x64 backend -> dispatcher architecture and must not special-case this guest PC.

## 2. Scope

In scope:

- decode SPECIAL funct `0x2d` as `R5900Instruction::Daddu`;
- add `R5900IrOpcode::Add64`;
- lower `DADDU rd,rs,rt` to `Add64`;
- validate the new IR opcode;
- execute it in the reference/interpreted executor;
- emit native Windows x64 code for it;
- mark `DADDU` dispatcher-v0 eligible;
- add focused decoder, IR, executor, x64 and dispatcher/startup-shaped tests;
- run complete Windows CI and pacing regressions;
- use the lawful external ELF only after GREEN to identify the next real unsupported boundary.

Out of scope:

- `DADD` overflow/trap semantics;
- `DADDI`, `DADDIU`;
- `DSUB`/`DSUBU`;
- `SW` or any later instruction merely visible after the current boundary;
- broad R5900 integer-ISA completion;
- graphics, VU, GS, IOP, SPU2, input or game boot claims;
- committing proprietary ELF bytes or assets.

## 3. Current evidence

The already integrated startup path reaches:

```text
0x00114ed0  27bdffb0  ADDIU sp,sp,-0x50
0x00114ed4  24020001  ADDIU v0,zero,1
0x00114ed8  ffbf0040  SD    ra,0x40(sp)
0x00114edc  03a0202d  DADDU a0,sp,zero
```

Entering the function after the previous validated JAL:

```text
sp = 0x01fffff0
ra = 0x00115118
```

The currently supported prefix produces:

```text
sp                  = 0x01ffffa0
v0.low64            = 0x0000000000000001
mem64[0x01ffffe0]   = 0x0000000000115118
```

The dispatcher then stops at `0x00114edc` because `DADDU` is not currently represented by the decoder/IR pipeline.

## 4. Architectural decision

Add a dedicated IR opcode:

```cpp
R5900IrOpcode::Add64
```

Do not reuse `AddWordSignExtend`.

Reason: `ADDU`/`ADDIU` currently implement 32-bit word addition followed by sign extension to 64 bits. `DADDU` performs an unsigned/no-trap 64-bit addition modulo 2^64. Reusing the word opcode would silently produce incorrect results whenever significant bits exist above bit 31 or when a carry crosses bit 31.

Do not bypass IR by implementing `DADDU` directly in the dispatcher or x64 backend. The reference executor remains the semantic oracle for differential testing.

## 5. Decoder contract

Add `Daddu` to `R5900Instruction`.

For primary opcode `0x00` (SPECIAL), funct `0x2d` must decode as:

```text
instruction       Daddu
instruction_class Alu
rs                bits 25..21
rt                bits 20..16
rd                bits 15..11
```

`DADDU` has no delay slot, no link behavior and no memory width.

The real word:

```text
0x03a0202d
```

must decode as:

```text
DADDU a0,sp,zero
rs = 29
rt = 0
rd = 4
```

`r5900_instruction_name(R5900Instruction::Daddu)` must return `DADDU` using the naming convention already used by the decoder.

## 6. IR lowering contract

For decoded:

```text
DADDU rd,rs,rt
```

when `rd != 0`, lowering emits exactly one instruction:

```text
opcode      Add64
destination GPR[rd]
write mode  Low64PreserveUpper64
inputs      GPR[rs], GPR[rt]
guest_pc    original PC
guest_raw   original raw word
```

When `rd == 0`, use the repository's existing discarded-GPR-zero-write behavior and emit one provenance-preserving `Nop` rather than an `Add64` write.

No immediate input is generated for `DADDU` v0.

## 7. `Add64` semantic contract

The semantic operation is:

```text
lhs    = GPR[rs].low64
rhs    = GPR[rt].low64
result = uint64(lhs + rhs) modulo 2^64
```

If destination is nonzero:

```text
GPR[rd].low64  = result
GPR[rd].high64 = previous GPR[rd].high64
```

No overflow exception is generated.

No flags, HI/LO registers, SA, FPR state, memory or unrelated GPRs are modified.

`GPR[0]` remains architecturally zero.

## 8. Aliasing semantics

Sources must logically be read from the pre-instruction state before the destination write.

Required correct cases:

```text
DADDU r4,r4,r5
DADDU r4,r5,r4
DADDU r4,r4,r4
```

The implementation may use host registers directly as long as these cases produce the same result as the reference executor.

## 9. Overflow/wrap semantics

`DADDU` is a no-trap operation. Arithmetic wraps modulo 2^64.

Required boundary examples:

```text
0xffffffffffffffff + 1 = 0x0000000000000000
0x8000000000000000 + 0x8000000000000000 = 0x0000000000000000
0x7fffffffffffffff + 1 = 0x8000000000000000
```

Tests must not use signed C++ overflow to model these cases. Operands/results are `std::uint64_t`.

## 10. IR validation contract

`Add64` must require:

- a present GPR destination;
- destination index in `[0,31]`;
- `R5900IrGprWriteMode::Low64PreserveUpper64`;
- exactly two inputs;
- both inputs of kind `Gpr`;
- both source register indices in `[0,31]`.

Immediate or FPR operands are malformed for `Add64` v0.

The validator should use existing integer-validation helpers where that yields the exact contract; it must not weaken validation for existing opcodes.

## 11. Interpreted executor contract

The reference executor implements `Add64` using unsigned 64-bit arithmetic.

Pseudo-code:

```cpp
const std::uint64_t lhs = state.gpr[src0].low64;
const std::uint64_t rhs = state.gpr[src1].low64;
const std::uint64_t value = lhs + rhs;
if (dst != 0u) {
    state.gpr[dst].low64 = value;
}
```

The executor must preserve `state.gpr[dst].high64` and normalize `GPR[0]` according to existing executor policy.

## 12. Windows x64 backend contract

Add native lowering parallel to `Or64`/`And64`:

```text
load input0 low64 -> RAX
load input1 low64 -> RDX
add rax,rdx
store RAX -> destination low64 if destination != r0
```

The intended arithmetic instruction encoding is ordinary x86-64 integer `ADD`; host overflow/carry flags are irrelevant and are not consumed.

The backend must not write the destination high64 half.

Native output must match the interpreted executor for normal, aliasing and wraparound cases.

## 13. Dispatcher contract

Add `R5900Instruction::Daddu` to `is_dispatcher_v0_eligible()`.

No other dispatcher policy changes are required.

Existing boundary-prefix semantics remain unchanged: if a later unsupported instruction occurs in the same analyzed basic block, the dispatcher executes only the supported prefix and reports the exact later boundary.

`DADDU` counts as one selected/executed guest instruction and participates in normal block caching and fast replay.

## 14. Startup-shaped acceptance

A synthetic test must model the real second-call prologue beginning at `0x00114ed0`:

```text
0x00114ed0  ADDIU sp,sp,-0x50
0x00114ed4  ADDIU v0,zero,1
0x00114ed8  SD    ra,0x40(sp)
0x00114edc  DADDU a0,sp,zero
```

Initial state:

```text
sp.low64 = 0x01fffff0
ra.low64 = 0x00115118
```

After the four supported instructions:

```text
sp.low64          = 0x01ffffa0
v0.low64          = 0x0000000000000001
a0.low64          = 0x0000000001ffffa0
mem64[0x01ffffe0] = 0x0000000000115118
```

The test must seed `a0.high64` with a nonzero sentinel and prove it is preserved.

The test must place an unsupported instruction immediately after the DADDU fixture or use the next real-shaped word only as a boundary sentinel. It must assert that DADDU executes and that the dispatcher stops at the following instruction rather than at `0x00114edc`.

A second run through the same dispatcher should verify cache/fast-replay behavior where the existing test harness makes that deterministic.

## 15. Test strategy

Implementation follows TDD RED -> GREEN.

### Decoder RED/GREEN

Add tests for:

- raw `0x03a0202d` decodes as `DADDU a0,sp,zero`;
- representative arbitrary `rs/rt/rd` fields;
- mnemonic string `DADDU`.

### IR lowering RED/GREEN

Add tests for:

- `DADDU -> Add64`;
- two GPR inputs in correct order;
- destination/write mode;
- guest provenance;
- `rd == 0 -> Nop`.

### Validator RED/GREEN

Cover:

- valid Add64;
- missing destination;
- wrong destination kind/write mode;
- wrong operand count;
- immediate/FPR rejection;
- invalid register indices.

### Executor RED/GREEN

Cover:

- ordinary 64-bit addition;
- values whose upper 32 bits affect the result;
- modulo-2^64 wrap;
- destination high64 preservation;
- source/destination alias cases;
- zero-register behavior;
- no unrelated state mutation.

### Native backend RED/GREEN

Differentially compare interpreted/native state for the same arithmetic corpus, including wrap and alias cases.

### Dispatcher RED/GREEN

Prove:

- `DADDU` is no longer an unsupported boundary;
- exact instruction accounting;
- high64 preservation;
- block cache behavior;
- a later unsupported instruction is reported at its own PC.

### Startup-shaped RED/GREEN

Cross the real-shaped prologue through `0x00114edc` and validate the state listed in section 14.

## 21. Completion criteria

The milestone is complete only when all of the following are true:

1. `0x03a0202d` decodes as `DADDU a0,sp,zero`.
2. DADDU lowers to validated `Add64` IR.
3. Interpreted and Windows x64 execution agree for normal/wrap/alias cases.
4. Destination high64 is preserved.
