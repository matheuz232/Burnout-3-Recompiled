# R5900 SW / Store32 v0 Design

Status: proposed design approved in chat; implementation not started.

Date: 2026-09-06

Base integration branch: `feature/r5900-or-v0`

Base SHA: `624142b544ac0f6a7623ff57a6845c70211a6519`

Working branch: `design/r5900-sw-v0`

## 1. Purpose

The current native R5900 startup path reaches the first real unsupported store after the DADDU milestone:

```text
0x00114ed0  ADDIU sp,sp,-0x50
0x00114ed4  ADDIU v0,zero,1
0x00114ed8  SD    ra,0x40(sp)
0x00114edc  DADDU a0,sp,zero
0x00114ee0  SW    v0,0x28(sp)   <- current real boundary
```

The existing decoder already recognizes `SW` as a word-width store. The missing support is downstream: IR lowering, IR validation, interpreted execution, the guest-memory callback ABI, the Windows x64 backend, and dispatcher eligibility/wiring.

This milestone adds the smallest correct `SW` execution path and then re-runs the lawful out-of-repository ELF diagnostic to discover the next real unsupported boundary.

This milestone does not claim game boot, playability, graphics, audio, input, or complete R5900 coverage.

## 2. Goals

1. Lower R5900 `SW` to a dedicated `Store32` IR opcode.
2. Extend the guest-memory callback ABI with a 32-bit write callback.
3. Execute `Store32` in the interpreted executor.
4. Execute `Store32` in the Windows x64 backend.
5. Wire `Store32` through the native block dispatcher and `Ps2MemoryMap::write_u32`.
6. Preserve exact memory-fault provenance and boundary-prefix behavior.
7. Add startup-shaped native regression coverage that crosses `SW @ 0x00114ee0`.
8. Validate cache replay for a deterministic synthetic `SW` block.
9. Run full Windows CI.
10. Use the user's lawful external ELF only as an out-of-repository diagnostic to identify the next real boundary.

## 3. Non-goals

The following are explicitly outside this milestone:

- `SB`, `SH`, `SWL`, `SWR`, `SWC1`, or other store instructions;
- load instructions;
- unaligned-store merge semantics;
- guest exception-vector delivery for address errors;
- TLB/MMU/cache emulation;
- changes to the 32 MiB EE main-RAM model;
- kernel/scheduler expansion unrelated to the observed boundary;
- GS/VU/rendering;
- IOP/SPU2/audio;
- controller/input integration;
- game boot or gameplay claims;
- committing any proprietary game executable bytes or assets.

## 4. Existing architecture reused

The milestone intentionally follows the already validated `Store64` and `Store128` paths.

Existing relevant components:

- `decode_r5900()` already decodes primary opcode `0x2B` as `R5900Instruction::Sw` with instruction class `Store` and memory width `Word`;
- `R5900IrOpcode` contains `Store64` and `Store128`;
- store IR uses the operand shape `(base GPR, value GPR, signed immediate)`;
- `R5900GuestMemoryAccess` currently exposes `write64` and `write128`;
- `Ps2MemoryMap` already exposes little-endian `write_u32`;
- the x64 backend uses helper calls for guest-memory stores;
- the dispatcher already converts native memory failures into deterministic guest PC/address/width diagnostics;
- the boundary-prefix fix prevents a later supported transfer from executing across an earlier unsupported/faulting instruction.

No decoder or RAM-model redesign is required.

## 5. R5900 SW semantics

For:

```text
SW rt, imm(rs)
```

v0 semantics are:

```text
base32  = low32(GPR[rs].low64)
offset  = sign_extend16(imm)
address = uint32(base32 + offset)
value   = low32(GPR[rt].low64)
```

The effective-address addition wraps modulo `2^32`.

Only the low 32 bits of the source GPR are stored. The source GPR's upper 32 bits of `low64` and all of `high64` are ignored.

The instruction does not modify CPU registers.

### 5.1 Alignment

`SW` requires a 4-byte-aligned effective address:

```text
(address & 0x3) == 0
```

There is no address rounding or alignment-down behavior.

A misaligned address returns the existing runtime error category `MemoryAccessFailure` in v0. Architectural address-error exception delivery is a later concern.

### 5.2 Endianness

The dispatcher adapter delegates to `Ps2MemoryMap::write_u32`, so the store uses the existing little-endian guest-memory representation.

### 5.3 Failure atomicity

For the production `Ps2MemoryMap` adapter:

- misalignment performs no guest-memory write;
- a missing callback performs no guest-memory write;
- an out-of-range `write_u32` fails before mutating guest memory;
- a failed `SW` does not modify CPU state;
- no guest instruction after the failing `SW` executes.

## 6. IR design

Add:

```cpp
enum class R5900IrOpcode {
    // ... existing opcodes ...
    Store32,
    Store64,
    Store128,
};
```

`Store32` has no destination and no GPR write mode.

Operand contract:

```text
inputs[0] = base GPR
inputs[1] = value GPR
inputs[2] = signed immediate
```

Lowering:

```cpp
case R5900Instruction::Sw: {
    auto ir = base_instruction(decoded, guest_pc, R5900IrOpcode::Store32);
    ir.inputs.push_back(gpr(decoded.rs));
    ir.inputs.push_back(gpr(decoded.rt));
    ir.inputs.push_back(immediate(decoded.signed_immediate()));
    result.instructions.push_back(ir);
    return result;
}
```

Provenance remains the decoded instruction's exact `guest_pc` and `guest_raw`, following all existing lowering paths.

## 7. IR validation

`Store32` validation mirrors the shape checks already used for `Store64`/`Store128`:

- destination absent;
- `write_mode == None`;
- exactly three inputs;
- input 0 is a valid GPR;
- input 1 is a valid GPR;
- input 2 is an immediate;
- immediate range is `[-32768, 32767]`.

Malformed shapes return `MalformedInstruction`.

Out-of-range GPR indices return `InvalidRegister`.

No alignment check belongs in IR validation because alignment depends on runtime register state.

## 8. Guest-memory callback ABI

Add a parallel callback type:

```cpp
using R5900GuestWrite32Fn = bool (*)(void* user,
                                     std::uint32_t address,
                                     std::uint32_t value) noexcept;
```

Extend:

```cpp
struct R5900GuestMemoryAccess {
    void* user{};
    R5900GuestWrite32Fn write32{};
    R5900GuestWrite64Fn write64{};
    R5900GuestWrite128Fn write128{};
};
```

This is an internal ABI used by the reference executor, native x64 blocks, tests, and dispatcher. All production dispatcher execution-context construction sites must wire `write32` alongside the existing callbacks.

The new dispatcher adapter is:

```cpp
bool ps2_memory_write32_adapter(void* user,
                                std::uint32_t address,
                                std::uint32_t value) noexcept {
    auto* memory = static_cast<runtime::Ps2MemoryMap*>(user);
    return memory != nullptr && memory->write_u32(address, value);
}
```

## 9. Interpreted executor

`Store32` execution computes:

```text
base    = uint32(state.gpr[base_index].low64)
offset  = uint32(int32(immediate))
address = uint32(base + offset)
source  = uint32(state.gpr[value_index].low64)
```

Then:

1. set `context.current_memory_guest_pc = ir.guest_pc`;
2. require `(address & 0x3) == 0`;
3. require non-null `memory.user` and `memory.write32`;
4. call `write32(user, address, source)`;
5. on failure, populate `memory_fault` and return `MemoryAccessFailure`.

Fault record:

```cpp
context.memory_fault = {
    true,
    R5900IrMemoryAccessKind::Store,
    ir.guest_pc,
    address,
    4u,
};
```

The error message distinguishes misalignment from a generic rejected/missing guest-memory write, parallel to `Store64`.

## 10. Windows x64 backend

Add a native helper parallel to the existing 64-bit helper:

```cpp
bool r5900_native_store32(R5900IrExecutionContext* context,
                          std::uint32_t address,
                          std::uint32_t value) noexcept;
```

Helper behavior:

- reject null context;
- require 4-byte alignment;
- require non-null user and `write32` callback;
- call `write32`;
- on failure, populate exact `Store` fault provenance with width `4`;
- return `false` on failure and `true` on success.

### 10.1 Native emitter

`emit_store32()` follows the `emit_store64()` helper-frame structure:

1. reload saved state/context pointers;
2. store `instruction.guest_pc` into `current_memory_guest_pc`;
3. compute EDX from low32(base) + signed imm16, modulo 32 bits;
4. load low32(source) into R8D;
5. load context into RCX;
6. call `r5900_native_store32`;
7. terminate the current native block immediately if the helper returns false;
8. reload state/context after successful helper return.

No alignment mask is emitted.

### 10.2 Helper-frame detection

`sequence_needs_helper()` must return true for any sequence containing:

```text
Store32
Store64
Store128
```

This applies to body and delay-slot sequences wherever the existing backend helper-frame policy is used.

## 11. Dispatcher integration

Add `R5900Instruction::Sw` to `is_dispatcher_v0_eligible()`.

Add `ps2_memory_write32_adapter()` and wire:

```cpp
execution_context.memory.user = &memory_;
execution_context.memory.write32 = &ps2_memory_write32_adapter;
execution_context.memory.write64 = &ps2_memory_write64_adapter;
execution_context.memory.write128 = &ps2_memory_write128_adapter;
```

at every dispatcher execution-context construction site.

Existing fault formatting already reports `width_bytes`, so a `Store32` failure naturally reports width `4`.

### 11.1 Dispatcher accounting

On successful `SW`:

- it counts as one executed guest instruction.

On faulting `SW`:

- the faulting `SW` is not counted as completed;
- supported instructions before it in the same block are counted;
- `next_pc` is the `SW` guest PC;
- later guest instructions are not executed.

Fast-cache replay must produce the same semantics and accounting as first execution.

## 12. Startup-shaped acceptance

The synthetic/native regression uses public ISA semantics and the already documented real guest PCs, without copying proprietary executable bytes beyond what is necessary to identify the instruction semantics.

Supported prefix:

```text
0x00114ed0  ADDIU sp,sp,-0x50
0x00114ed4  ADDIU v0,zero,1
0x00114ed8  SD    ra,0x40(sp)
0x00114edc  DADDU a0,sp,zero
0x00114ee0  SW    v0,0x28(sp)
```

Entry state inherited from the prior milestone:

```text
sp = 0x01fffff0
ra = 0x00115118
```

Expected supported-prefix state after `SW`:

```text
sp.low64               = 0x0000000001ffffa0
v0.low64               = 0x0000000000000001
a0.low64               = 0x0000000001ffffa0
mem64[0x01ffffe0]      = 0x0000000000115118
mem32[0x01ffffc8]      = 0x00000001
```

The test must also verify that bytes adjacent to the 4-byte `SW` destination remain unchanged, proving the store width is exactly four bytes.

A synthetic unsupported sentinel after the `SW` may be used to prove that the dispatcher boundary advances beyond `0x00114ee0`. That sentinel must be generated from public ISA knowledge and must not copy the real next proprietary word from the user's ELF.

## 13. Focused synthetic Store32 tests

### 13.1 Lowering and validation

Cover:

- positive offset;
- negative offset;
- base `r0`;
- value `r0`;
- exact guest provenance;
- no destination/write mode;
- invalid operand count;
- invalid operand kind;
- invalid GPR index;
- immediate below `-32768`;
- immediate above `32767`.

### 13.2 Interpreted execution

Cover:

- ordinary aligned write;
- low32-only source semantics;
- high32/high64 source bits ignored;
- signed negative offset;
- 32-bit effective-address wrap;
- 4-byte alignment requirement;
- missing callback;
- rejected callback;
- exact PC/address/width-4 fault provenance;
- no CPU-state mutation;
- failed write prevents later IR execution;
- adjacent bytes unchanged on successful write.

### 13.3 Windows x64 differential execution

Compare interpreted and native outcomes for:

- ordinary store;
- low32-only source;
- negative offset;
- address wrap;
- misalignment;
- callback failure;
- fault provenance;
- state preservation.

### 13.4 Dispatcher/cache

Cover:

- `SW` eligible in a normal block;
- successful write into EE RAM;
- width-4 memory failure reporting;
- prefix accounting before fault;
- no execution after fault;
- deterministic synthetic `SW + supported transfer` replay;
- second execution uses the existing cache/fast-cache path without recompilation when guest words are unchanged.

## 14. Lawful external ELF diagnostic

After all synthetic/native gates are green, use the user's legally supplied ELF outside the repository to determine the next real unsupported boundary after `SW @ 0x00114ee0`.

Rules:

- do not commit the ELF;
- do not commit dumps or proprietary executable sequences;
- do not add a copied raw next instruction word to tests/spec/docs;
- record only the minimum diagnostic facts needed for the next milestone: guest PC, decoded mnemonic/operands, and relevant derived state;
- clearly distinguish a local diagnostic model/probe from a Windows-native end-to-end external dispatcher run.

The next boundary is intentionally unknown in this design. It becomes authoritative only after the Store32 implementation passes its native gates and the lawful diagnostic is executed.
