# R5900 LD / Load64 v0 Design

Status: approved design, pending implementation
Date: 2026-09-07
Base: `feature/r5900-createsema-v0` @ `da66f8ab37138b596f5a57b756d4817c481b3fad`

## Goal

Advance the native Burnout 3 startup path beyond the observed `LD @ 0x00114f08` boundary by adding a narrowly scoped, reusable 64-bit guest-load path to the existing R5900 IR, reference executor, Windows x64 backend, and native block dispatcher.

This milestone does not add a general interpreter fallback, does not bypass the production ELF loader, and does not add proprietary game data to the repository.

## Architectural approach

`LD rt, imm(rs)` lowers to a generic IR opcode named `Load64`. Guest memory remains abstracted behind `R5900GuestMemoryAccess`; the execution ABI gains a `read64` callback rather than exposing `Ps2MemoryMap` internals to generated x64 code. The portable reference executor and Windows x64 backend consume the same callback contract, and the dispatcher adapts it to the existing `Ps2MemoryMap::read_u64` implementation.

This keeps the existing store architecture intact and establishes the smallest reusable read-side primitive for later load instructions.

## Instruction semantics

For `LD rt, imm(rs)`:

```text
base32  = low32(GPR[rs].low64)
offset  = sign_extend16(imm)
address = uint32(base32 + offset)
value   = guest_read64(address)
```

Requirements:

- effective-address arithmetic wraps modulo `2^32`;
- the effective address must be strictly 8-byte aligned;
- no alignment-down is permitted;
- exactly eight guest bytes are read;
- guest memory is little-endian through the existing memory-map contract;
- on success with `rt != 0`, `GPR[rt].low64 = value`;
- `GPR[rt].high64` is preserved;
- when `rt == 0`, the guest read still occurs and can fault, but the loaded value is discarded;
- all unrelated CPU state is preserved;
- a failed load must not partially modify the destination register or later guest state.

## IR contract

Add `R5900IrOpcode::Load64`.

A valid `Load64` instruction has one GPR destination, `R5900IrGprWriteMode::Low64PreserveUpper64`, and two inputs in this exact order: base GPR and signed 16-bit immediate. The destination identifies `rt`; the loaded value comes from guest memory.

`lower_r5900_instruction()` lowers decoder instruction `R5900Instruction::Ld` to this shape. Unlike ordinary discarded writes, `LD $zero,...` must not lower to `Nop`, because the memory access and possible fault remain architecturally observable.

## Guest-memory ABI

Extend `R5900GuestMemoryAccess` with:

```cpp
using R5900GuestRead64Fn = bool (*)(void* user,
                                    std::uint32_t address,
                                    std::uint64_t* value) noexcept;
```

and a `read64` member. The callback returns `true` only when all eight bytes are readable and writes the complete value through the non-null output pointer. The caller performs the architectural alignment check before invoking the callback.

Existing `write32`, `write64`, and `write128` callbacks retain their current signatures and behavior.

## Memory-fault model

Extend `R5900IrMemoryAccessKind` with `Load` while preserving `None` and `Store`.

A failed `Load64` records `active=true`, `access=Load`, the exact LD guest PC, the exact unmasked effective address, and `width_bytes=8`. Failures include misalignment, missing memory user, missing `read64`, and callback rejection. The execution result is `R5900IrExecutionError::MemoryAccessFailure`.

## Reference executor

The portable executor computes the 32-bit wrapped effective address, validates strict 8-byte alignment, invokes `read64`, and commits the destination low64 only after the callback succeeds. Destination high64 remains byte-for-byte unchanged. `LD` targeting GPR zero must still perform the memory access before zero normalization.

## Windows x64 backend

Add a native helper analogous to the existing store helpers:

```cpp
bool r5900_native_load64(R5900IrExecutionContext* context,
                         std::uint32_t address,
                         std::uint64_t* value) noexcept;
```

The helper rejects null context, enforces 8-byte alignment, requires `memory.user` and `memory.read64`, delegates the guest read, records the exact Load fault on failure, and does not modify CPU state.

Generated x64 records `current_memory_guest_pc`, computes the wrapped low32 effective address without alignment masking, calls the helper with temporary storage, returns failure if the helper fails, commits the value to destination low64 only after success and only for nonzero destination, preserves high64, and restores saved state/context pointers after the helper call. Any sequence containing `Load64` uses the existing helper frame.

## Dispatcher integration

Add a `Ps2MemoryMap` adapter that calls `read_u64` and copies the optional value to the callback output. Populate `memory.read64` on cold, exact-cache, and fast-cache execution paths; admit `R5900Instruction::Ld`; preserve existing cache checks; format load faults as `load width 8 bytes at guest address ...`; count only instructions completed before the faulting LD; and stop at the exact LD PC.

No interpreter fallback is introduced.

## Validation strategy

Development uses TDD RED -> GREEN with focused commits and complete regression gates.

IR/lowering coverage proves correct destination/base/immediate, signed offsets, high64-preserving write mode, observable `LD $zero,...`, and malformed-shape rejection. Reference-executor coverage proves aligned success, 32-bit wrap, offsets, callback value flow, high64 preservation, observable GPR-zero loads, misalignment/missing-callback/callback-rejection faults, exact provenance, transactional destination behavior, and stop-before-later-IR behavior.

Windows x64 differential tests cover successful loads and address arithmetic; native-only tests cover helper failure, exact fault provenance, destination preservation, and observable `LD $zero`. Existing Store32/Store64/Store128 and control-flow suites remain mandatory regressions.

Dispatcher coverage proves cold compile, successful LD, repeated fast replay without recompilation, exact-word cache validation, aligned success, misaligned/unmapped failure, exact completed-prefix accounting, and load commit before a later unsupported boundary.

The CreateSema startup-shaped synthetic fixture is extended beyond `LD @ 0x00114f08` using public ISA encodings and synthetic data only. The first newly encountered unsupported instruction becomes the next recorded startup boundary. Optional complete external ELF validation remains opt-in and CI never contains or downloads game files.

## Non-goals

This milestone does not implement other guest loads, MMIO/scratchpad/GS/VU/IOP/SPU2 spaces, TLB/exception delivery, interpreter fallback, broader semaphore scheduling, rendering/input/audio/game initialization/menu/gameplay, relaxed ELF validation, or reconstruction of missing proprietary bytes.

## Acceptance criteria

1. `LD` lowers to validated `Load64` IR.
2. The portable reference executor implements the specified semantics and exact Load fault provenance.
3. The Windows x64 backend executes the same semantics through `read64`.
4. The dispatcher wires `read64`, admits `Ld`, and preserves cache/fault accounting.
5. Synthetic native startup advances beyond `0x00114f08` to a newly identified lawful boundary.
6. Existing store/control-flow/syscall/startup regressions remain green.
7. Complete Windows CI, pacing, and package gates pass before `CI_VALIDATED`.
8. No proprietary Burnout 3 bytes or artifacts are committed.
