## Result

`R5900 LD / Load64 v0` is implemented and validated through the portable IR/reference executor, Windows x64 backend, native dispatcher/cache, and synthetic startup-shaped path.

This milestone does **not** establish that Burnout 3 boots, renders, reaches menus, or is playable. Those subsystems remain incomplete.

## Architectural contract

`LD rt, imm(rs)` lowers to `R5900IrOpcode::Load64` with:

```text
base32  = low32(GPR[rs].low64)
offset  = sign_extend16(imm)
address = uint32(base32 + offset)
value   = guest_read64(address)
```

Validated semantics:

- effective-address arithmetic wraps modulo 2^32;
- strict 8-byte alignment; no align-down;
- success writes destination low64 only;
- destination high64 is preserved;
- `LD $zero` still performs the memory access and can fault;
- failure is transactional with respect to the destination;
- precise fault metadata records `Load`, guest PC, address and width 8;
- later IR/control-flow effects do not execute after a failing load.

## Memory ABI

The execution memory bridge now includes:

```cpp
using R5900GuestRead64Fn = bool (*)(
    void* user,
    std::uint32_t address,
    std::uint64_t* value) noexcept;
```

`R5900GuestMemoryAccess` carries `read64` alongside the existing write callbacks. `R5900IrMemoryAccessKind` now distinguishes `Load` from `Store`.

The dispatcher adapter reads from `Ps2MemoryMap::read_u64` and wires `read64` in normal, exact-cache and fast-cache execution paths.

## Windows x64 implementation

The native helper returns the loaded value in RAX. On alignment, bridge, or guest-memory failure it records the precise Load64 fault in the execution context.

Generated code:

1. publishes the current guest memory PC;
2. computes the 32-bit wrapped effective address;
3. calls the Load64 helper;
4. checks `memory_fault.active`;
5. returns from the native block immediately on failure;
6. writes RAX to destination low64 only after success;
7. discards the successful result when destination is GPR0.

The helper result intentionally does not occupy `[rsp+0x30]`; that scratch slot is already used to preserve indirect-transfer targets across helper-containing delay slots.

## Dispatcher behavior

Validated dispatcher behavior includes:

- decoded `LD` is eligible for native v0 execution;
- `SD + LD + JAL` executes as one native block;
- `SW + LD + J + NOP` executes as one native block;
- repeated execution can use fast-cache replay;
- guest memory is read on every execution rather than captured at compile time;
- load faults preserve exact guest PC/address/width and completed-prefix accounting;
- load diagnostics say `load width 8 bytes`, while store diagnostics remain `store ...`;
- destination registers remain unchanged on failed loads.

## Synthetic startup acceptance

The startup-shaped CreateSema fixture uses public ISA encodings and synthetic data only. Its relevant tail is:

```text
CreateSema host boundary
SW returned semaphore ID
LD ra,0x40(sp)
unsupported synthetic sentinel
```

Acceptance proves that the native startup path now executes through the previously observed `LD @ 0x00114f08` boundary. The load restores the saved RA low64 and preserves RA high64; the dispatcher stops only at the deliberate sentinel after the load.

The same fixture is executed again to validate cache replay while CreateSema remains an executed host boundary rather than a cached host result.

## External real-game validation status

The historical external ELF copy available during earlier diagnosis is incomplete:

```text
available size                  3,589,632 bytes
load segment requires through   4,073,344 bytes
```

The production loader correctly rejects it. The implementation did not relax loader checks or invent missing game bytes.

Consequences:

- the synthetic/native test proves the old `LD @ 0x00114f08` implementation boundary is crossed;
- the next real Burnout 3 instruction/HLE boundary is **not known from complete production execution yet**;
- identifying it requires a complete, lawful, user-supplied ELF;
- no proprietary game bytes or external-file artifacts are committed to the repository.

The optional external mode is:

```powershell
.\build\Release\r5900_block_dispatcher_createsema_windows_tests.exe C:\Games\Burnout3\SLUS_210.50
```

It uses the production loader and native dispatcher, requires execution to move beyond `0x00114f08`, verifies SetupThread, SetupHeap and two CreateSema calls, and prints the newly reached stop location/diagnostic.
